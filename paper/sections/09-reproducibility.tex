\paragraph{Task and training settings (v1).}
Hidden size 128; encoder 64 features (affine + tanh on 38 input channels); AdamW, learning rate $10^{-3}$, weight decay $0.01$, gradient clipping $1.0$; batch size 32 (16 paired prefix/query examples); 1,500 steps; validation every 100 steps on 32 pairs per horizon; training horizons $\{1,2,4,8,16\}$ with balanced arms; evaluation horizons $\{1,2,16\}$ with 256 pairs each; two driver pairs per horizon; 512 cloud cues and 256 probe test cues; ridge $0.01$; one CPU thread for data generation.

\paragraph{State shapes.}
GRU complete state: 128 hidden coordinates. LSTM complete state: $[h,c]$ with 128 + 128 = 256 coordinates, flattened in the saved manifest order. Encoder features and the QUERY selector are inputs, not state. The planned GC-LSTM adapter has state $2NH$ with the node ordering recorded.

\paragraph{Numerical settings.}
Native float32 recurrence; centering and eigendecomposition in float64; variance comparisons at zero absolute and $10^{-5}$ relative tolerance; covariance eigenvalue absolute tolerance $10^{-12}$ times the recomputed cloud trace. Periodicity protocol: CUDA matmul and cuDNN TF32 disabled; FP64 replay casts fixed weights and all inputs and runs WRITE and body from the zero state; closure tolerances FP32 $(10^{-7},10^{-5})$ and FP64 $(10^{-10},10^{-8})$ for states, FP32 $(10^{-6},10^{-5})$ and FP64 $(10^{-10},10^{-8})$ for Jacobian arrays; adapter/native equivalence FP32 $(10^{-6},10^{-5})$ and FP64 $(10^{-12},10^{-10})$; ordered-product/direct-map agreement FP32 $(10^{-5},10^{-4})$ and FP64 $(10^{-10},10^{-8})$; central finite differences at $\epsilon\in\{10^{-4},10^{-5},10^{-6}\}$ with absolute $10^{-8}$ and relative $10^{-4}$ bounds; relative denominators floored at $10^{-12}$.

\paragraph{Determinism and reduced-precision flags (v1 training).}
The v1 training code (\texttt{pilot.py}) neither set nor recorded the CUDA matmul and cuDNN TF32 flags or \texttt{float32\_matmul\_precision}; with PyTorch's default \texttt{cudnn.allow\_tf32=True} the A100 and H100 pilots may have used TF32 inside cuDNN RNN kernels, which cannot be checked from the saved artifacts (implementation audit, sections 4--5). The provenance field \texttt{deterministic\_algorithms: True} written by the pilot is a constant in the source, not a measured property of the run. The audit verified that two identical CPU repeat runs produce bitwise-identical checkpoints and identical $\delta_2$ and $\delta_{16}$ (only \texttt{runtime\_seconds} differs); CUDA repeat-run determinism is unverified, as no GPU repeat run exists. The TF32-disabled setting stated above applies to the checkpoint-only periodicity protocol only. Design v2 records both TF32 flags and the matmul precision in provenance. \evidence{executed-verified}
